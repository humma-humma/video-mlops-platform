# Read-only diagnostic export check — 2026-10-18

Two previously persisted jobs were exported through the loopback FastAPI service without submitting, retrying or cancelling a job. The [CPU model bundle](live_cpu_job.json) retained deployment identity, the artifact revision, one successful attempt, lifecycle events and stage timings. It omitted the text input/output and did not copy a job ID, trace ID or API key. The [recovery job bundle](live_recovery_job.json) retained timeout and retry history but returned `insufficient_evidence` when analyzed alone: the service API does not record the external worker-kill action. The [recorded interruption report bundle](pilot/recorded_worker_interruption.json) includes that external timeline and yields `worker_interruption` with citations.

The exporter made only five bounded GET requests per job. Liveness, current metrics and release identity are collection-time context, not proof of which release produced an old result. Both exported bundles passed schema and integrity validation in the offline analyzer. The [eight-case pilot](pilot/evaluation.json) separately checks the rule/citation contract; its synthetic variants do not measure generalization.

Two additional previously persisted real-GPU jobs were exported as [first/cold](live_gpu_cold.json) and [second/warm](live_gpu_warm.json) bundles. Their [offline comparison](live_gpu_comparison.json) confirms the same deployment, input hash, model revision and lineage hashes, then reports per-stage deltas with citations. The observed model-load stage fell from 31.98 seconds to zero; this is the recorded model-reuse behavior, not a controlled estimate of overall GPU capacity.
